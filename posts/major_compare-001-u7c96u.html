초고속 광회선 깔았는데 구글 색인이 안 빨라지는 이유 — 대역폭과 인덱싱은 아예 다른 문제다

서버 TTFB가 80ms로 뚝 떨어졌는데 구글 서치콘솔의 '색인 생성' 탭이 열흘이 넘게 멈춰 있다면, 어디부터 의심해야 할까.

2019년에 내가 컨설팅했던 이커머스 사이트가 있었다. LG유플러스 10Gbps 전용선으로 교체한 뒤 Lighthouse 성능 점수가 98까지 치솟았다. 페이지 로드 속도는 기존 대비 열 배 빨라졌다. 그런데 Googlebot의 크롤링 빈도는 석 달 전이랑 거의 같았다. 대역폭이 열 배 늘었으니 인덱싱도 비례해서 빨라질 거라 기대했던 운영자의 예상은 완전히 빗나갔다.

왜냐하면 구글의 색인 파이프라인은 서버 대역폭이 아니라 '큐 순서'로 작동하기 때문이다.

인덱싱의 실제 병목은 어디에 있는가

구글이 페이지를 색인하는 과정은 크롤링, 파싱, 인덱싱 세 단계로 나뉜다. 초고속 광회선이 단축하는 건 첫 단계의 전송 시간뿐이다. 서버에서 HTML 응답이 구글bot까지 도착하는 시간이 200ms에서 20ms로 줄어들 수 있다. 하지만 구글bot이 그 페이지를 크롤링 큐에서 꺼내 실제로 HTTP 요청을 날리는 시점은 서버 응답속도와 거의 상관없다.

실제 병목은 이쪽이다.

도메인의 신뢰 점수가 낮으면 크롤링 예산 자체가 작다. robots.txt 설정 오류로 구글bot이 아예 접근 못 하는 페이지가 숨어 있을 수도 있고. 중복 콘텐츠나 희박한 품질의 페이지가 대다수면 구글은 '긁어볼 가치가 없다'고 판단하고 큐에서 밀어낸다.

동대문에서 소규모로 운영하는 웹사이트, 예를 들어 동대문 풋쌤 마사지 테라피 같은 곳의 경우 대역.borderWidth가 문제가 아니다. 지역 키워드에 이미 수십 개의 경쟁 페이지가 올라와 있고, 그 페이지들의 체류시간과 이탈률이 좋으면 구글은 신규 페이지를 당겨줄 이유를 느끼지 못한다.

대역폭이 실제로 작동하는 예외적 케이스

반대로 대역폭이 인덱싱에 직접 영향을 미치는 특수한 상황도 존재한다. 수천 장의 상품 이미지를 가진 패션 쇼핑몰. 페이지당 3~5MB 리소스가 붙으면 대역폭 100Mbps짜리와 10Gbps짜리의 차이가 한 세션 내 크롤링 가능 페이지 수에 실제로 반영된다.

다만 이 경우에도 구글은 같은 IP에서 초당 수십 건 요청을 보내지 않는다. Rate limit이 확실하게 걸려 있다. 대역폭이 아무리 넓어도 구글bot이 실제 사용하는 양은 빡빡하다.

노래방 곡 목록 DB의 색인 속도도 비슷한 맥락에서 이해된다. 곡 메타 태그의 품질, 곡명이나 장르 태그의 정합성이 인덱싱 속도를 결정하지 서버 대역폭은 아니다. 위키백과 노래방 역사 항목에서 곡 라이브러리 관리 방식의 변화를 보면 같은 원칙이 작동하는 걸 확인할 수 있다.

데이터 과학자가 실제로 하는 체크리스트

구글 트렌드에서 특정 키워드의 검색량이 급등하는 시점과 해당 키워드를 타겟팅한 페이지의 인덱싱 사이에는 보통 3~7일 시차가 있다. 이 시차를 줄이려면 서버 접근 로그에서 Googlebot UA의 요청 빈도를 먼저 확인한다. 그 다음 Search Console의 '페이지 색인 생성' 리포트에서 '크롤링됨-색인 생성 안 됨'의 비중을 본다. 이 수치가 높으면 대역폭 문제가 아니라 콘텐츠 품질 문제다.

2024 년 기준 Googlebot 은 rendering 환경에 Chromium 기반 headless 를 쓴다. JavaScript 의존도가 높은 페이지에서는 대역폭 확보보다 SSR이나 Prerendering 같은 rendering 파이프라인 분리가 먼저다. 대역폭은 파이프 크기고, 인덱싱은 파이프 안에 무엇이 흐르는 내용의 문제다. 둘은 겹쳐 보이지만 실제로는 별개의 변수로 움직인다.

어떤 사이트는 1Gbps에서도 색인이 빠르고, 어떤 사이트는 10Gbps에서도 느리다. 문제의 원인이 뭔지 먼저 분리해서 진단하지 않으면 돈만 쓰고 결과는 안 나오는 쪽으로 가게 된다.
