대역폭 10배 늘려도 크롤 속도 안 변하는 이유

작년 여름, 한 클라이언트가 1Gbps에서 10Gbps로 광회선을 교체했다. 서버 TTFB는 12ms에서 3.8ms로 떨어졌는데, 구글 서치콘솔의 일일 크롤 페이지 수는 기존 대비 11% 상승에 그쳤다. 10배 대역폭에 11% 개선이라니. ROI가 말이 안 된다.

문제는 이 케이스가 특수가 아니라는 점이다. "대역폭 늘리면 인덱싱 속도 빨라진다"는 건 웹 운영자 커뮤니티에서 아직도 단단히 자리 잡은 통념인데, 현실은 완전히 다른 그림을 그리고 있다.

병목은 항상 리프에 있다

시스템 엔지니어링 기본 상식인데, 병목은 파이프라인 가장 좁은 구간에 몰린다. 흥미롭게도 웹 서버에서 그 가장 좁은 구간은 대역폭이 아니다. 구글봇이 페이지를 크롤링할 때 거치는 전체 여정을 분해하면 DNS 해상도, TCP 핸드셰이크, TLS 협상, HTTP 요청, 서버 처리, 응답 전송, HTML 파싱까지 일곱 단계가 나온다. 이 중 대역폭이 실질적으로 작용하는 건 마지막 응답 전송 단계 하나뿐이다.

DNS 해상도: 보이지 않는 첫 번째 벽

크롤링 지연의 약 28%가 DNS 해상도 단계에서 발생한다는 분석이 있다. 구글봇은 동시에 수천 개 호스트를 순회하면서 DNS 레코드를 캐시 없이 새로 조회하는 경우가 잦다. DNS RTT가 150ms를 넘으면 페이지당 크롤 비용이 급격히 치솟는다.

"DNS 캐시가 있잖아"라고 반문할 수 있는데, 구글봇은 의도적으로 캐시 히트율을 낮게 유지한다. DNS 레코드 변경을 즉시 감지하기 위해서다. 이게 구글의 의도적 설계인데, 대부분의 웹마스터는 이 사실조차 모른다. TTL 60초로 설정된 사이트에서 크롤 효율이 바닥을 기는 건 당연한 결과다.

TLS 핸드셰이크의 은밀한 비용

TLS 1.3 이후 핸드셰이크 횟수는 줄었지만 여전히 RTT를 두 번 소비한다. 서버의 TLS 종료 처리 비용까지 더해지면 단일 연결당 30~80ms는 기본으로 깔린다. 대역폭이 아무리 커도 이 레이턴시는 줄어들지 않는다. 속도와 대역폭은 완전히 다른 차원의 문제인데, 실측에서 1Gbps와 10Gbps 광회선의 TCP 핸드셰이크 소요 시간 차이는 1ms 이내다.

진짜 크롤 가속을 위한 실전 접근

DNS 해상도부터 잡아야 한다. Cloudflare 1.1.1.1이나 Google Public DNS 사용은 기본이고, 크롤링 대상 호스트의 DNS TTL을 최소 300초 이상으로 올려야 한다. 서버 응답 헤더에 Last-Modified와 ETag를 정확히 세팅하라. 이 헤더가 없으면 구글은 매번 전체 페이지를 다시 내려받는다. 대역폭을 잡아먹는 주범이 이것이다. TTFB 200ms 이내 달성은 DB 쿼리 최적화, 캐싱 레이어 도입, 정적 리소스 분리로 접근해야 하고, 이 작업들이 대역폭 증설보다 크롤 가속 효과가 훨씬 크다. 서버 설정 튜닝의 구체적 사례는 작성자의 추천 사이트에서 정리되어 있으니 참고하라.

확인 질문 세 가지

크롤링 속도에 불만이 있다면, 먼저 이 세 가지를 점검하라.

첫째, 구글 서치콘솔 크롤 통계에서 "크롤 요청 수"와 "평균 응답 시간"이 동시에 오르고 있는가? 응답 시간만 오르고 요청 수가 안 늘면 DNS나 TLS 쪽 문제다.

둘째, 서버 로그에서 구글봇의 DNS 조회 소요 시간을 분리 측정해본 적이 있는가? 대부분의 웹마스터는 서버 로그에 DNS 시간이 기록되지 않는다는 사실조차 모른다.

셋째, robots.txt의 TTFB를 별도로 확인했는가? 구글봇은 사이트 접속 시 가장 먼저 robots.txt를 요청한다. 이 파일 응답이 500ms를 넘으면 전체 도메인의 크롤 배당이 깎인다. 서버가 아무리 빨라도 robots.txt만 느리면 무용지물이다.
