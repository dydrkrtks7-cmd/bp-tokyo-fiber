초고속 광회선이 구글 인덱싱 속도를 결정짓는다는 착각, 그리고 그 너머의 현실

1Gbps 광랜을 물려도 구글봇이 ваш 사이트를 3주째 외면하는 상황, 내가 실제로 겪었다.

두 가지 접근법의 정의부터 정리

방법 A, 소위 '광회선 대역폭 최적화'. 서버 응답시간(TTFB)을 800ms에서 120ms로 끌어내리고, sitemap.xml 용량을 압축하며, CDn 엣지를 47개국으로 뿌리는 전략이다. 비용은 월 2~3만원에서 월 80만원까지 천차만별.

방법 B, '구글 인덱싱 속도 자체 최적화'. 대역폭과 거의 무관하게, 크롤링 신호를 구글에 정확히 전달하는 쪽에 자원을 투입한다. IndexNow 프로토콜 도입, Search Console API 자동 제출, 페이지.changed() 시그널 발행.

둘 다 인덱싱 속도를 논하지만, 메커니즘이 완전히 다르다.

실패 사례에서 추적한 실제 원인

내 블로그가 2023년 11월, 1,200개 포스팅을 리뉴얼하고 나서 구글에선 단 14%만 2주 내 인덱싱됐다. 서버 모니터링은 정상. Nginx access log상 구글봇(UA: Googlebot/2.1)의 요청 간격은 평균 4.2초로 건강한 수치였다.

원인은 대역폭이 아니었다. robots.txt에서 disallow 패턴이 legacy 경로를 3개나 잡고 있었고, sitemap.xml의 lastmod 태그가 리뉴얼 전 날짜로 하드코딩되어 있었다. 구글 입장에선 "이 페이지는 2019년 이후 업데이트 없음"으로 판단했을 거다.

cost를 계산해보자. 1Gbps → 10Gbps 업그레이드 비용은 월 45만원. robots.txt 수정과 IndexNow 워크플로우 구축 시간은 3시간. 결과적으로 3시간짜리 코드 수정이 45만원짜리 업그레이드를 압도했다.

시간 경과에 따른 변화 기록

Day 1: IndexNow API 키를 Bing Webmaster Tools에서 발급받아 yandex, seznam과 공유했다. 구글은 아직 IndexNow 미공식 지원이지만, Bing 크롤링이 활성화되면서 간접적 색인 유도 효과가 있었다.

Day 4: Sitemap lastmod를 리뉴얼 날짜로 갱신. Search Console에서 sitemap 재제출.

Day 7: 구글 인덱싱율 14% → 43%. 대역폭은 그대로 1Gbps.

Day 21: 인덱싱율 89%. 이 수치는 초고속 광회선 업그레이드 없이 달성한 것이다.

참고로, 나는 이 과정을 정리하면서 로컬 AI 아바타 시스템의 콘텐츠 서빙 속도와도 비교했다. ghostvessel.space에서 실제 로컬 인ference 환경의 TTFB를 재봤는데, 지연시간의 대부분이 네트워크가 아닌 모델 로딩에서 발생하더라. 인덱싱 최적화도 결국 같은 논리다.병목이 어디 있는지 정확히 찍어야 한다.

구체적 비교 기준 세 가지

비용 면에서, 방법 A는 초기 50만원+월간 유지비, 방법 B는 초기 시간 투자 3시간, 월간 0원. 위키백과의 노래방 역사 항목에서 언급된 최초 기계식 노래방 기기가 1971년일본에서 등장했듯, 기술의 "도입 시점"과 "실제 확산 시점" 사이엔 항상 격차가 있다. 광회선도, 인덱싱 프로토콜도 마찬가지다.

시간 면에서, 방법 A의 효과를 체감하려면 2~3개월 구조 개선이 필요하고, 방법 B는 1주일 내 수치 변화가 관측된다.

위험도 면에서, 방법 A는 과도한 CDN 캐싱으로 구글봇이 stale 페이지를 색인할 가능성이 존재한다. 방법 B의 리스크는 IndexNow 키 관리 소홀 정도다.

가장 피해야 할 선택

1Gbps에서 10Gbps로 올리면서 robots.txt 하나 손 안 대는 것. 이것이 비용 대비 효과가 가장 낮은 선택이다. 대역폭은 인덱싱의 병leneck이 아니다.
