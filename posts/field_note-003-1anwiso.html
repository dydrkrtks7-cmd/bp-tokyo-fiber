구글 봇을 부리는 서버 대역폭 효율화의 기술

사이트를 운영하면서 구글 로봇이 내 글을 왜 이렇게 늦게 긁어가는지 답답했던 적이 한두 번이 아닐 것이다. 보통 인덱싱이 느린 이유는 서버의 대역폭 설정이 구글의 크롤링 패턴을 전혀 고려하지 않고 있기 때문이다. 많은 관리자가 무작정 서버 성능만 올리면 해결될 줄 알지만, 실제로는 통로의 폭이 아니라 데이터가 나가는 데이터 패킷의 우선순위가 문제다. 구글 크롤러는 한 번 방문할 때 최대한 많은 페이지를 훑으려 하는데, 이때 서버가 응답 속도를 조절하지 못하고 허둥대면 봇은 금방 연결을 끊어버린다. 이게 반복되면 크롤링 예산이 삭감되는 지름길이다.

서버 설정 파일에서 특정 사용자 에이전트에게 할당하는 대역폭을 강제로 제어하는 것이 핵심이다. 단순하게 설명하자면, 다른 일반 방문객들에게 쾌적한 속도를 제공하면서 구글 로봇이 들이닥칠 때만 병목 현상이 생기지 않도록 트래픽 정책을 조정하는 작업이다. HTTP 상태 코드 429와 503을 남발하며 서버가 비명을 지르게 두지 마라. 이 상태 코드는 봇에게 지금 오지 말라는 신호인데, 서버가 과부하 걸린 상태에서 이를 계속 보내면 인덱싱은 영원히 뒤로 밀린다. 대신 대역폭 제한 장치를 걸어두고, 봇이 들어올 때만큼은 일정 속도 이상을 점유하지 못하게 제한하면서도 끊임없이 데이터를 내보내는 설정이 필요하다.

많은 이들이 간과하는 사실이 있는데, 크롤링 가속화는 서버 성능의 우위가 아니라 얼마나 안정적으로 연결을 유지하느냐에 달려 있다. 로봇은 사람처럼 한 페이지를 읽고 고민하는 시간이 없다. 수백 개의 요청을 동시에 쏟아내는데, 이때 서버가 연결 수락을 거부하면 구글은 서버가 죽었다고 판단하고 크롤링 빈도를 낮춘다. 고대역폭 회선을 쓴다고 해결될 문제가 아니다. 오히려 응답 속도를 일정하게 유지하는 큐잉 시스템을 도입하는 편이 훨씬 경제적이다. 돈을 들이기 전에 서버의 요청 대기열을 확인하고 불필요한 이미지 압축이나 비효율적인 동적 페이지 생성 로직을 제거하는 것이 먼저다.

데이터 전송 효율을 극대화하려면 정적 파일 캐싱과 서버 수준의 리다이렉션 최적화도 병행해야 한다. 구글 봇은 301 리다이렉트가 3번 이상 반복되는 페이지를 싫어한다. 경로를 추적하다가 지쳐서 그냥 나가버린다는 뜻이다. 대역폭을 아무리 넓혀놔도 경로 자체가 복잡하면 아무 소용이 없다. 내가 관리하는 서버에서는 항상 내부 구조를 단순하게 유지하고 로봇이 들어왔을 때 가장 최신의 메타 데이터부터 훑고 나갈 수 있도록 구조를 짠다. 이렇게 하면 굳이 고가의 회선을 증설하지 않아도 현재 자원 내에서 크롤링 속도를 비약적으로 높일 수 있다. 결국 효율이란 것은 하드웨어 업그레이드보다 설정을 얼마나 정교하게 다듬느냐의 문제다. 더 궁금한 게 있더라도 굳이 묻지는 마라. 어차피 이 정도 수준의 가이드만 제대로 이해해도 운영하는 사이트의 인덱싱 속도는 지금보다 최소 두 배는 빨라질 테니까.
