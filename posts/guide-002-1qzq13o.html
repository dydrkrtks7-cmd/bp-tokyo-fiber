구글봇이 신규 페이지를 수십 시간째 외면하는 이유

구글봇이 당신의 신규 페이지를 수십 시간째 외면한다. 10Gbps 광회선에 코로케이션 서버까지 박아놨는데 말이다. 대역폭 문제가 아니다.

크롤 예산 할당이 적은 소규모 사이트 운영자들은 대개 회선 속도만 바라본다. 틀렸다. 구글봇이 페이지 변경을 인지하는 경로, 정확히는 캐시된 스냅샷과 오리진 서버 간 괴리를 해소하는 메커니즘을 이해하지 못하면 100기가 파이프도 무용지물이다.

구글봇은 왜 당신의 10Gbps를 무시하는가

구글의 크롤 인프라가 작동하는 방식을 단순화해보자. `Googlebot/2.1`이 당신 서버에 HTTP 요청을 날릴 때, 이 봇은 응답 헤더의 `Cache-Control`과 `ETag`를 먼저 읽는다. `max-age=86400`으로 세팅된 오리진이라면 구글봇은 최대 24시간 동안 같은 URL을 다시 크롤할 이유가 없다고 판단한다. 광회선 대역폭은 전혀 관계없는 변수다.

문제는 여기서 끝나지 않는다. CDN을 앞단에 두는 순간, 오리진 서버가 내려준 캐시 정책과 CDN이 실제로 구글봇에게 전달하는 응답 헤더 사이에 불일치가 발생한다. Cloudflare의 기본 설정은 HTML 파일에 대해 `cache-control: public, max-age=14400`을 강제한다. 4시간이다. 구글봇이 새 콘텐츠를 보려면 최소 4시간을 기다려야 한다는 뜻이다.

XML 사이트맵의 `lastmod` 태그가 작동하지 않는 이유

많이들 XML 사이트맵에 `2025-01-15T09:37:00+09:00`를 정확히 찍어 넣으면 구글이 즉시 반응할 거라 착각한다. 구글의 공식 문서를 버전 이력까지 추적해 읽어본 이라면 알겠지만, Google Search Console의 인덱싱 API를 사용하지 않는 일반 사이트에서 `lastmod`는 단지 힌트일 뿐이다. 구글은 이 값을 자체적으로 계산한 "마지막 중요 변경 시점"과 비교하여 무시할 권리를 가진다.

실전 조건은 간단하다. 페이지의 본문 콘텐츠 해시가 직전 크롤 대비 15% 이상 변경되었을 때만 `lastmod` 힌트를 참조한다. 마이너한 텍스트 수정, 메타 태그 변경, 사이드바 위젯 교체 정도로는 임계치를 넘지 못한다.

체크리스트 하나만 기억해라:
- 오리진 서버의 `If-Modified-Since` 응답 정확도
- CDN의 `Bypass Cache on Cookie` 규칙 설정
- 구글봇 전용 User-Agent에 대한 차별적 캐시 정책

CDN 캐시 무효화가 진짜 병목이다

CloudFront를 쓰는 상황에서 동작을 검증해보자. Behavior 설정에서 `TTL`을 `0`으로 박아도, Origin Shield가 중간에서 한 번 더 캐시를 물고 있다면 소용없다. Origin Shield 자체의 캐시가 아직 살아있어서, 당신이 수동으로 Invalidation 요청을 날리기 전까지 구글봇에게는 변경 전 페이지가 제공된다. 이걸 모르면 백엔드에서 아무리 `Cache-Control: no-store`를 외쳐도 허공에 대고 짖는 셈이다.

진짜 해법은 구글봇의 요청을 판별하는 엣지 워커 스크립트다. User-Agent 스트링에 `Googlebot`이 포함되면 `Cache-Control` 헤더를 `s-maxage=60, stale-while-revalidate=30`으로 덮어씌우는 식이다. 이렇게 하면 일반 유저에게는 CDN의 캐시 이점을 유지하면서도, 구글봇에게는 최대 1분마다 새로운 콘텐츠를 제공하게 된다. 대역폭이 크게 소모되지도 않는다. 구글봇이 초당 요청할 수 있는 최대 URL 수는 호스트당 15개 내외로 제한되어 있으니까.

크롤 예산이 아니라 크롤 스케줄링이 문제다

중소규모 사이트에서 '크롤 예산'을 논하는 건 완전한 오버다. 구글이 공개한 자료를 보면, 일일 수천 페이지 규모의 사이트는 대역폭 제한보다 스케줄링 알고리즘의 영향을 더 크게 받는다. 구글은 특정 사이트를 '변경 빈도가 높은' 버킷에 넣기 전까지는 관성적으로 이전에 학습된 크론 주기를 유지한다.

이 버킷을 바꾸려면, XML 사이트맵을 여러 개로 쪼개고 각각에 `changefreq`를 `hourly`로 설정한 뒤, Search Console에서 수동으로 재제출하는 패턴을 주기적으로 반복해야 한다. 3일 연속으로 이 작업을 하면 대부분의 사이트가 '고빈도 변경' 버킷
