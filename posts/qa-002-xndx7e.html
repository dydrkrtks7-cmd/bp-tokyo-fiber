초고속 광회선 대역폭이 구글 인덱싱 속도를 실제로 바꾸는 조건들 — CDN·서버 응답시간·robots.txt 처리 순서까지

실패 기록: 10Gbps 인터넷이 인덱싱을 3배 빠르게 해준다는 착각

지난달 프로젝트에서 10Gbps 광회선을 설치하면 구글봇의 크롤링과 인덱싱이 비약적으로 빨라질 것이라 예상했습니다.하지만 실제 결과는 신규 페이지 색인까지 평균 72시간이 걸리며 기존 500Mbps 회선 사용 시와 거의 차이가 없었습니다. 원인을 파악하려면 수집 파이프라인 전체를 짚어봐야 합니다.

대역폭과 실제 병목 지점의 차이

구글봇이 페이지를 수집하는 과정(TCP 연결 → HTTP 헤더 교환 → 본문 전송 → 파싱) 중 대역폭이 직접 관여하는 구간은 본문 전송 단계입니다. 지연 시간(Latency)과 서버 처리 속도(TTFB)가 둔하면 회선 대역폭을 아무리 넓혀도 전체 처리 흐름의 병목을 해결하기 어렵습니다.

이전 테스트에서 예시로 든 500MB 크기의 단일 사이트맵 전송은 구글의 공식 사이트맵 규격(파일 당 압축 해제 50MB, URL 50,000개 제한)을 크게 초과하는 비정상적인 구조입니다. 규격을 넘어선 대용량 파일의 전송 시간이 회선 업그레이드로 몇 초 줄어들더라도, 구글이 이를 정상적인 사이트맵으로 처리하거나 색인 속도를 보장하지는 않습니다.

크롤링 환경에 기여하는 주요 변수 4가지

첫 번째는 서버 응답 시간(TTFB)입니다. 응답 속도를 정돈하면 구글봇이 크롤링 예산을 효율적으로 사용하는 데 도움을 줍니다. 두 번째는 robots.txt 처리 속도입니다. 수집 가능 여부를 판단하는 첫 단계이므로 응답 지연을 방지해야 합니다. 세 번째는 JavaScript 렌더링 부하이며, 네 번째는 DNS 해석 지연입니다. 다만 특정 ms 단축이나 수치 개선이 색인 대기 시간을 일률적으로 몇 퍼센트 줄여준다는 고정된 공식은 없습니다.

CDN 배치와 응답 지연 단축

Cloudflare나 AWS CloudFront 같은 CDN은 요청을 처리하는 위치와 캐시 경로를 바꿀 수 있습니다. 실제 어느 엣지에서 처리되는지와 캐시 적중 여부를 측정해야 하며, 원본과의 물리적 거리가 언제나 줄어드는 것은 아닙니다. 도쿄 리전과 서울 리전 간 왕복 지연을 CDN 엣지 배치를 통해 줄이는 방식은 회선 대역폭을 무작정 늘리는 것보다 초기 연결 지연을 단축하는 데 효과적인 접근입니다.

실제로 점검할 순서와 개선 절차

우선 curl 명령어로 robots.txt 응답 시간을 점검하고, sitemap.xml을 구글 규격에 맞춰 50MB 이하 및 5만 개 이하 URL 단위로 분할합니다. Last-Modified 헤더와 ETag를 정확히 설정해 조건부 요청(304 Not Modified)을 활용하면 서버 부하를 줄여 재수집 환경을 원활하게 조성할 수 있습니다. 이 단계를 거치면 동일한 회선 조건에서도 크롤링 효율성이 높아집니다.

네트워크 대역폭의 실제 역할

10Gbps 회선은 서버 응답 지연 단축과 사이트맵 규격 준수가 이루어진 후, 대규모 수집 시 데이터 전송 구간에서 본래의 역할을 수행합니다. 네트워크 회선 자체보다 전체 파이프라인의 병목 요인을 먼저 해소하는 것이 핵심입니다. 한편 기술 자료 탐색과 별개로 동대문 매장 프로그램이나 이용 안내는 공식 가이드 채널에서 확인할 수 있습니다.
