초고속 광회선 대역폭이 구글 인덱싱 속도를 실제로 바꾸는 조건들 — CDN·서버 응답시간·robots.txt 처리 순서까지

실패 기록: 10Gbps 인터넷이 인덱싱을 3배 빠르게 해준다는 환상

지난달 한 고객사 프로젝트에서 10Gbps 광회선을 설치하고 구글 인덱싱 속도가 비약적으로 빨라질 것이라 확신했다. 결과는 참담했다.新규 페이지 색인까지 평균 72시간. 기존 500Mbps 회선과 거의 차이 없었다. 원인을 파헤치기 시작했다.

진짜 병목은 대역폭이 아니었다

구글봇이 페이지를 수집하는 과정을 역추적하면, TCP 연결 설정 → HTTP 헤더 교환 → 본문 전송 → 파싱 순서인데, 대역폭이 관여하는 구간은 '본문 전송'뿐이다. 나머지 세 단계는 레이턴시와 서버 처리 속도가 지배한다. 광회선 업그레이드로 지연시간이 4ms에서 1ms로 줄어들어도, 서버 측 Time to First Byte(TTFB)가 800ms이면 전체 흐름에서 의미가 희석된다.

실제 측정 예시: 동일 500MB sitemap.xml을 기준으로 1Gbps vs 10Gbps 전송 시간 차이는 약 3.2초다. 하지만 구글봇이 sitemap을 완전히 처리하는 데 걸리는 시간은 보통 15~40초. 대역폭 차지 비율은 전체의 10% 내외다.

인덱싱 가속에真正 기여하는 변수 4가지

첫 번째는 서버 응답 시간이다. TTFB를 200ms 이하로 유지하면 구글봇의 재방문 주기가 짧아진다. 두 번째는 robots.txt 처리 속도. 응답이 늦으면 구글봇이 첫 수집 자체를 지연한다. 세 번째는 페이지 렌더링 속도,特别是 JavaScript 의존도가 높은 SPA 구조에서 렌더러 대기 시간이 치명적이다. 네 번째, 그리고 간과되는 것이 DNS 해석 시간이다. 1차 DNS 조회가 300ms 이상 걸리면 다음 수집 단계부터 전체적으로 딜레이가 누적된다.

CDN 배치 위치가 대역폭을 압도하는 이유

Cloudflare 또는 AWS CloudFront 같은 CDN을 사용하면 원본 서버와 구글봇 간 물리적 거리가 줄어든다. 도쿄 리전과 서울 리전 간 왕복 레이턴시는 평균 60ms인데, CDN 엣지가 서울에 있으면 8ms까지 떨어진다. 이 차이가 구글봇의 첫 페이지 수집 시간에 직접 반영된다. 초고속 회선 없이도 CDN만으로 인덱싱 대기 시간을 30% 이상 단축한 사례는 수두록하다.

실제로 작동하는 최적화 절차

robots.txt 응답 시간을 먼저 측정한다. curl -s -o /dev/null -w "%{time_total}\n" https://도메인/robots.txt 명령어로. 0.5초 이상이면 서버 설정부터 손봐야 한다. 그 다음 sitemap.xml 크기를 50MB 이하로 분할하고, Last-Modified 헤더를 정확히 설정한다. ETag와 If-Modified-Since 조합이 구글봇의 조건부 요청을 활성화시키면 서버 부하가 줄면서 재수집 주기가 빨라진다. 마지막으로 페이지 렌더링 속도를ighthouse 기준 2.5초 이내로 맞춘다. 이 세 단계를 거치면, 같은 광회선으로도 인덱싱 대기 시간이 평균 40~50% 감소하는 걸 확인할 수 있다.

원래의 10Gbps 회선이 쓸모없었던 건 아니었다

그 프로젝트의 10Gbps 회선은 sitemap 분할과 TTFB 최적화를 적용한 이후, 대규모 콘텐츠 업데이트 시 구글봇의 대량 페이지 수집 속도에 분명한 차이를 보였다. 문제는 회선이 아니라 회선이 작동하는 위치를 잘못 파악한 것이었다. 광대역폭이 빛나려면 그 전 단계의 모든 파이프가 막힘 없어야 한다. 자세한 서버 설정 기준과 단계별 절차는 공식 가이드 채널에서 확인 가능하다.
